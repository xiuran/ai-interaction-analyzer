# 反模式库

AI 协作中常见的反模式集合。发现新模式时追加到对应分类。

---

## 1. 信息缺失

### 1.1 裸命令

**表现**：prompt 只有一个动词，没有对象和上下文。
**示例**：`fix it` `优化` `重构` `好了`
**影响**：AI 必须猜目标，大概率猜错 → 浪费 1-2 轮。
**修正**：至少给出文件名或函数名。

### 1.2 无锚点引用

**表现**：提到"那个文件""上面那个""之前的那个"但没给具体路径。
**示例**：`改那个接口` `上面那个类有问题`
**影响**：AI 可能引用错误的上下文。
**修正**：使用完整路径或 `filename:line` 格式。

### 1.3 隐含期望

**表现**：说"不对"但不说哪里不对、期望什么。
**示例**：`不是这样` `错了` `换一种`
**影响**：AI 猜测被拒原因，经常在同一个错误方向上微调。
**修正**：说清"哪里不对" + "期望什么样"。

## 2. 效率

### 2.1 否定循环

**表现**：连续 3 轮以上否定 AI 产出。
**根因**：初始 prompt 缺乏清晰目标，或用户脑中有具体画面但没表达出来。
**信号**：session 中否定词密度 > 30%。
**修正**：第 2 次否定时停下来，写一个更完整的 prompt。

### 2.2 Session 膨胀

**表现**：单个 session 超过 50 轮且交付物不明确。
**根因**：目标漂移、中途加需求、或把不相关任务塞进同一个 session。
**信号**：turns > 50 且任务类型切换 ≥ 2 次。
**修正**：一个 session 一个目标。复杂任务拆成多个 session。

### 2.3 过度确认

**表现**：AI 每步都问确认，用户不断说"继续"。
**根因**：prompt 没有预授权自主执行。
**信号**：session 中 > 30% 的 prompt 是 `继续/ok/yes/对/go ahead`。
**修正**：初始 prompt 加上"直接执行，不需要逐步确认"。

---

## 3. 行为模式

### 3.1 目标漂移

**表现**：一个 session 内任务方向变了 3 次以上。
**示例**：`写个 API` → `先看下日志` → `先修这个 bug` → `还是先写文档`
**根因**：用户在探索过程中发现新问题，没意识到已经漂移了。
**修正**：检测到漂移时开新 session，原 session 保持聚焦。

### 3.2 过度委托

**表现**：把手动操作更快的事情委托给 AI。
**示例**：`这个文件多少行` `这个变量怎么拼`
**信号**：多个 < 10 字符的非命令 prompt。
**影响**：等 AI 回复可能比自己做还慢。
**修正**：简单查询直接用 CLI 工具。

### 3.3 上下文碎片化

**表现**：连续多个 prompt 之间没有逻辑关联，每次都要重建上下文。
**根因**：用户脑中有完整的任务链但每次只发一步。
**修正**：写一个完整的 prompt 描述整个任务链（步骤 1 → 步骤 2 → 步骤 3）。

---

## 4. 质量

### 4.1 复制粘贴 Prompt

**表现**：粘贴整段错误日志或代码块，不加任何说明。
**影响**：AI 只能猜意图（修复？解释？忽略？）。
**修正**：粘贴后加一句："请解释这个错误"或"请修复这个问题"。

### 4.2 多目标混合

**表现**：一个 prompt 包含 4 个以上不相关的目标。
**示例**：`写个 API，顺便修那个 bug，再看下性能，还有文档也更新一下`
**影响**：AI 可能遗漏部分目标，或每个都只做得很浅。
**修正**：拆成多个 prompt，每个聚焦一个目标。

---

## 5. AI 行为反模式

### 5.1 API/方法名编造

**表现**：AI 调用二方包/三方包时凭训练数据猜测方法签名，编译报错后才发现方法不存在。
**示例**：使用 `ResultGeneralModel.getData()` 而实际方法是 `getReturnValue()`；凭空写出支付宝字段名。
**检测信号**：用户说"编译报错""方法不存在""这个 API 不对"。
**根因**：AI 没有先通过 Read/find 确认 JAR 源码中的真实方法签名。
**修正规则**：调用任何不熟悉的 API 前，必须先读源码或反编译确认方法签名和返回值类型。

### 5.2 只看签名不读方法体

**表现**：参照旧实现做新功能时，只看了方法签名/变更清单，不读方法体理解真实逻辑，在新旧差异点上踩坑。
**示例**：照搬云闪付的 PostCashierManager 用法，不理解扩展点机制差异。
**检测信号**：用户说"你有深度理解代码吗""无脑抄""照猫画虎"。
**根因**：AI 倾向于用最小上下文完成任务，但代码改动需要理解"为什么这么写"而不只是"写了什么"。
**修正规则**：参照旧实现时，必须 Read 旧方法体，列出新旧差异点，再针对性改动。

### 5.3 排查时编造因果链

**表现**：排查线上问题时，手里只有片段信息就急于给确定性结论，编造因果关系。
**示例**：声称"6 点恢复是因为 OSCAR_SCHEDULE_OPEN_TIME 开关"，实际该开关早已过期无影响。
**检测信号**：用户说"不要瞎编""你分析的对吗""需要我提供信息，可以叫我提供"。
**根因**：AI 对"不确定"有偏见，倾向于给一个听起来合理的解释，而不是承认信息不足。
**修正规则**：排查时先列"已确认事实"和"还需要的信息"两个清单，信息不足时禁止给确定性结论。

### 5.4 改一个丢三个

**表现**：收到一条修改意见后大面积重写，导致之前已验证通过的内容丢失。
**示例**：用户反馈一个图表问题，AI 重写整个文档，把之前调好的效率数据、分析维度全删了。
**检测信号**：用户说"你疯了一样改""把其他好的地方改坏了""之前不是好好的吗"。
**根因**：AI 用 Write 全量覆盖而不是 Edit 精准替换，没有"最小化修改"意识。
**修正规则**：收到修改意见后，先确认修改范围并标注"其他不动"，用增量 Edit 而非全量 Write。

### 5.5 前端不验证就交付

**表现**：生成前端代码后只关注功能逻辑，不验证视觉效果和交互体验，样式丑或不可用。
**示例**：表单因子选择器放在页面最下面，用户操作不便；样式多次反馈仍无改善。
**检测信号**：用户说"样式难看""人用不了""你是瞎吗""好看吗""好用吗"。
**根因**：AI 工具链缺少 UI 验证环节（截图/预览），但也没主动声明需要人工验证。
**修正规则**：前端代码变更后必须验证视觉效果。无法截图时显式声明"样式需要人工验证"。

### 5.6 遗留代码清理不彻底

**表现**：做功能变更时只改了主路径代码，废弃的注释、import、常量、过程代码没清理。
**示例**：AB 实验删了但相关常量和注释还在；应该统一用枚举但各处散落魔法常量。
**检测信号**：用户说"为什么还有""过程代码保留干什么""不能统一用枚举吗"。
**根因**：AI 聚焦于"加新功能"而忽略"清理旧代码"，没有做全局一致性检查。
**修正规则**：代码变更后必须全局检查废弃 import/注释/常量，确保全局一致性。

### 5.7 输出不可理解

**表现**：AI 输出使用抽象代号（X/Y/A/B/方案一）、特殊称谓或怪异格式，用户看不懂。
**示例**：提问时用"做 X 和 Y"代替具体名称；输出中用用户不接受的称谓。
**检测信号**：用户说"我都不知道你在说什么""驴唇不对马嘴""看不懂""什么东西"。
**根因**：AI 在内部推理时用了缩写代号，直接暴露到输出中而不是展开成具体名称。
**修正规则**：输出中禁止使用抽象代号提问，每个选项/概念必须用具体名称完整列出。

---

## 使用说明

1. 分析引擎检测到反模式时引用本文档提供改进建议
2. 新发现的模式追加到对应分类（1-4 章为用户侧，第 5 章为 AI 侧）
3. 每个模式必须包含：表现、检测信号、根因、修正方法
4. 引擎根据检测结果匹配对应的改进建议
