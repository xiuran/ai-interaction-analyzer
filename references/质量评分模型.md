# Prompt 信息完整度模型

> 这个分数衡量的是**形式层面**——prompt 给了 AI 多少可直接开工的信息，
> **不是判断 prompt 好坏**。一条简短的专家指令可能得分很低却完全没问题。
> 因此分档用中性描述（信息充分 / 基本够用 / 偏简 / 极简），不用价值判断词（优 / 差）。

## 设计理念

好的 prompt 不一定长，但必须让 AI 无需猜测就能理解意图。

核心原则：
1. **信息完整性** > 信息量：10 个清晰的字比 100 个含糊的字强
2. **可执行** > 可理解：AI 应该能立刻开始工作
3. **不惩罚简短**：斜杠命令和清晰的短指令不应被扣分——「极简」是中性描述，不是缺点

## 五维度评分模型

### 维度 1：适当长度（满分 20）

| 范围 | 分数 | 原因 |
|------|------|------|
| < 10 字符 | 0 | 信息可能不足（除非是明确的命令） |
| 10-19 | 5 | 短但可能足够 |
| 20-49 | 10 | 简洁合理 |
| 50-500 | 20 | 信息密度最佳区间 |
| 500+ | 15 | 详细但可能冗余 |

### 维度 2：具体引用（满分 25）

匹配模式：
- 文件路径：`/path/to/file.ext` 或 `~/xxx`
- 行号引用：`filename.ext:42`
- 代码符号：`ClassName.methodName`

命中 → +25。这是区分"模糊请求"和"可执行指令"的关键维度。

### 维度 3：明确目标（满分 20）

关键词：`我要` `需要` `目标` `期望` `希望` `要求` `实现` `完成` `修复` `修改` `添加` `删除`

命中 → +20。表示用户表达了明确的意图动词。

### 维度 4：提供上下文（满分 20）

关键词：`因为` `原因` `背景` `之前` `目前` `问题是` `上下文`

命中 → +20。表示用户提供了"为什么"的信息。

### 维度 5：目标聚焦（满分 15）

| 目标关键词数量 | 分数 | 解释 |
|---------------|------|------|
| 0 | 0 | 没有明确目标 |
| 1-2 | 15 | 聚焦，好 |
| 3 | 10 | 稍多但可接受 |
| 4+ | 5 | 多目标混合，有遗漏风险 |

## 评分示例

### 高分（100/100）

> 修复 src/services/auth.ts:47 的空指针异常，目前 getSession() 在用户未登录时返回 null 但调用方没处理

- 长度：20（50-500 字符）
- 引用：25（`src/services/auth.ts:47`）
- 目标：20（"修复"）
- 上下文：20（"目前...用户未登录时..."）
- 聚焦：15（单一目标）
- **总分：100**

### 中等（45/100）

> 帮我修一下那个登录的 bug

- 长度：10（20-49 字符）
- 引用：0（没有文件路径）
- 目标：20（"修"）
- 上下文：0（没有背景）
- 聚焦：15（单一目标）
- **总分：45**

### 低分（5/100）

> 好了

- 长度：0（< 10 字符）
- 引用：0
- 目标：0（"好了"是状态词，不是目标）
- 上下文：0
- 聚焦：0
- **总分：0 → 下限兜底 5**

## 未来方向

1. **LLM 辅助评分**：用小模型判断 prompt 的"可执行性"
2. **个性化权重**：根据用户协作风格调整各维度权重
3. **对比评分**：对比同一任务的不同 prompt 表达方式
4. **跨 session 追踪**：同一话题跨 session 时，追踪 prompt 质量是否提升
